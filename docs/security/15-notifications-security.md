# Security 15: Notifications Security

## 1. Threat Model & Security Principles

The notification system processes user push tokens, email addresses, and real-time operational alerts. Strict defensive principles are enforced across backend, database, and client integrations.

---

## 2. Key Security Controls

### 2.1 Backend-Only Credentials
- **FCM Service Account**: The Firebase service account JSON containing private keys is strictly server-side. It is loaded via path specified in `FIREBASE_CREDENTIALS_FILE` or Application Default Credentials. It is **never** committed to version control, bundled into client builds, or logged.
- **Resend API Key**: Configured via `RESEND_API_KEY` on the backend only. Never accessible to frontend clients or returned in API responses.
- **VAPID Public Key**: The Firebase Web Push VAPID key is an asymmetric public key (`FIREBASE_WEB_PUSH_VAPID_PUBLIC_KEY` / `PUBLIC_FIREBASE_WEB_PUSH_VAPID_PUBLIC_KEY`). It is public configuration used by browsers to subscribe to push services.

### 2.2 Server-Derived Identity & Anti-IDOR
- All notification endpoints (`/api/v1/notifications/...`) derive the recipient's user identity from the verified JWT access token (`middleware.GetUserID(ctx)`).
- Queries for listing notifications, fetching unread counts, and marking notifications as read enforce `WHERE recipient_user_id = $auth_user_id`.
- Marking a notification read belonging to another user returns `404 NOT_FOUND` (preventing information disclosure and IDOR).

### 2.3 Lock-Screen Payload Minimization
- Lock-screen push payloads generated by FCM are visible on locked phones and desktop notification banners.
- In accordance with data minimization principles:
  - Payloads contain only general event summaries: e.g. "Visitor Waiting: Delivery Agent", "New Maintenance Bill Generated".
  - Financial account numbers, full visitor phone numbers, government IDs, and access secrets are **strictly excluded** from push payloads.
  - The notification contains an `action_url` and `reference_id` pointing the user to the authenticated app interface where full details are loaded under standard authorization.

### 2.4 Transactional Email Security & HTML Sanitization
- Resend transactional emails are generated with server-rendered templates.
- Any user-controlled text (e.g. member names, society names, announcement titles, bill remarks) is HTML-escaped (`html.EscapeString`) before embedding in email bodies to prevent HTML/script injection in email clients.
- Recipient email addresses are resolved strictly from authenticated server records. Client callers cannot specify arbitrary destination email addresses.

### 2.5 Token Management & Multi-Device Isolation
- A user may register multiple devices (e.g., home laptop, work laptop, phone).
- When FCM returns invalid-token errors (`UNREGISTERED`, `INVALID_ARGUMENT`), only the specific device record is marked `INACTIVE`. Other active device tokens belonging to the user remain unaffected.
- On user logout, the specific client's device token is deactivated via `DELETE /api/v1/notifications/devices/{device_id}`.

### 2.6 Outbox & Worker Isolation
- The `notification_outbox` worker processes jobs with `SKIP LOCKED`, avoiding row lock contention.
- Network requests to FCM and Resend are executed with 10-second timeouts **outside** database transactions to prevent connection pool exhaustion and transaction lock hoarding during network slowdowns.
